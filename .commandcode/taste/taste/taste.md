# Taste
- Prefers features to run fully client-side in the browser, with no servers and no server-side compilation. Confidence: 0.7
- Prefers to begin new feature work with a minimal proof-of-concept (e.g. a simple standalone HTML page) before doing the full integration. Confidence: 0.6
- Keeps generated build artifacts committed to the repo (e.g. a built multi-MB runtime bundle, plus build output dirs) so a fresh clone runs as-is, rather than gitignoring them and requiring a build step. Confidence: 0.5
- Wants compiler integrations packaged as a reusable factory — `createXCompiler({ baseUrl })` returning `compile(code, options) → { code, info }` — where `baseUrl` addresses the package's own assets, so the caller just hands over source plus options and gets back JS to run in the result page. Confidence: 0.75
- Compilers must run in a classic (non-module) web worker with no DOM access; compiling and running are separate concerns (compile in the worker, run the produced JS in the page). Confidence: 0.8
- Prefers runtimes that work as-is without a wrapper package, and only packages the pieces that genuinely need wrapping. Confidence: 0.6
- Prefers non-breaking language/feature additions: add new ids alongside whatever exists rather than repointing an existing name (and keep aliases from colliding with the existing ones). Confidence: 0.5
- For npm/JS dependencies in the browser playground, prefers runtime ESM loaded from a CDN resolved via automatically generated import maps (the LiveCodes approach) over build-time bundling from node_modules. Confidence: 0.6
- Evaluates technology choices against ecosystem conventions — wants to know whether a capability is common/idiomatic practice in the language's community (and what the standard toolchain does) before investing in it. Confidence: 0.5
- Before building out a capability, wants a check for prior art: whether a comparable/well-known peer project already solves the same problem, and if it is open source, exactly how it does it (each time asked "Is X open-source? Can we find out how they handle this?"). Confidence: 0.6
- When considering whether to add or keep another engine/language alongside ones already supported, wants it framed as a head-to-head capability comparison — what the new option uniquely adds, overlapping strengths, and each side's advantages/disadvantages — not a standalone feature list. Confidence: 0.55
- Prefers a language be offered as at most two variants: a lightweight one plus one full (typically wasm-backed) compiler, differentiated in a way users notice. Dislikes adding extra engines that are incomplete or approximate versions of the same language — "three partial answers" is worse than one partial plus one real. Confidence: 0.7
- Values a "full" engine variant being genuinely complete in language semantics (real core/stdlib behavior, real analyzer errors, working macros) and would prioritise closing those gaps over ecosystem/breadth features. Confidence: 0.6
- Wants the agent to carry work through to implementation and verification rather than pausing at a plan or diagnosis — after a proven approach, the expectation is to make the code change and report results, not to hand back next steps. Confidence: 0.75
- Expects the agent to keep iterating autonomously until the feature actually works, not to stop and report partial status or hand back a diagnosis/"next experiment" — explicitly says to continue and not stop until it's working. Confidence: 0.7
- Won't accept a known bug documented as a "known limitation"; when a limitation is fixable, wants the real/principled fix, not a workaround or a note in the docs. Confidence: 0.5
- Wants new capabilities proactively hardened against many usage contexts: after one case is fixed, expects the agent to try other/varied uses of the same feature (edge cases, nesting, alternate names, multiple instances) to surface latent bugs and fix them, rather than treating the reported case as done. Confidence: 0.5
- Wants a new language's starter template to be the same familiar shape as every other language's starter (a "Hello, <Language>!" heading with the language's logo and a click-counter button), i.e. uniform boilerplate across languages rather than a bespoke one-off template. Confidence: 0.55
- Expects a new language/feature to be integrated across its full surrounding surface — language info panel, starter template, docs, e2e test, i18n strings — matching existing repo conventions, not just the core module. Confidence: 0.5
- When a list of remaining gaps/limitations is reported, wants it benchmarked against well-known peer/competitor implementations of the same kind — classifying each item as inherent to the category, a packaging/curation gap, or a deliberate design difference we'd not actually want to change — rather than presented as an undifferentiated to-do list. Confidence: 0.5
- Treats shipping as a checkpoint requiring an explicit go/no-go review: before releasing, asks whether something is ready as-is or what must be added/fixed first, expecting hard blockers to be separated from nice-to-haves (including anything only typechecked but never executed). Confidence: 0.5
- Handles the release/implementation side steps himself — publishing packages to npm, building, starting the dev server, renaming language ids, adding new mechanisms (e.g. a deprecation flag), copying over docs — then hands back with a bare "continue"/"carry on", expecting the agent to read the current repo state (git status/diff) first and build on the user's edits rather than re-applying or restoring its own earlier version. Confidence: 0.55
- Names language variants after the engine that backs them, as a suffix (e.g. `clojurescript-cherry`, `clojurescript-selfhosted`), rather than vague labels like `-wasm` or "light"/"full". Confidence: 0.5
- Prefers a superseded but previously shipped language/feature be kept under an explicit deprecation mechanism rather than deleted, while an addition that never delivered distinct value gets removed outright and cleanly (no leftover references anywhere, regenerated generated files rather than hand-edited). Confidence: 0.5
- Before locking in a curated/bundled feature set and syncing or publishing it, wants the completeness question asked first ("should we add more X? Are these all the stdlib?") — i.e. an opportunity to widen the scope before it is frozen, rather than only syncing exactly what is already built. Confidence: 0.45
- Sequences work into discrete, gated stages with an explicit definition-of-done for the current one, and parks known follow-up work as a separate later task rather than bundling it into one pass (e.g. "do this so that the only remaining thing is publish, then we can look into cljs.test"). Wants the stage driven to the point where only his own out-of-band step (publishing) remains. Confidence: 0.45
