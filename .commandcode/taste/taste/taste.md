# Taste
- Prefers features to run fully client-side in the browser, with no servers and no server-side compilation. Confidence: 0.7
- Prefers to begin new feature work with a minimal proof-of-concept (e.g. a simple standalone HTML page) before doing the full integration. Confidence: 0.6
- Keeps generated build artifacts committed to the repo (e.g. a built multi-MB runtime bundle, plus build output dirs) so a fresh clone runs as-is, rather than gitignoring them and requiring a build step. Confidence: 0.5
- Wants compiler integrations packaged as a reusable factory — `createXCompiler({ baseUrl })` returning `compile(code, options) → { code, info }` — where `baseUrl` addresses the package's own assets, so the caller just hands over source plus options and gets back JS to run in the result page. Confidence: 0.75
- Compilers must run in a classic (non-module) web worker with no DOM access; compiling and running are separate concerns (compile in the worker, run the produced JS in the page). Confidence: 0.8
- Prefers runtimes that work as-is without a wrapper package, and only packages the pieces that genuinely need wrapping. Confidence: 0.6
- Prefers non-breaking language/feature additions: add new ids alongside whatever exists rather than repointing an existing name (and keep aliases from colliding with the existing ones). Confidence: 0.5
- For npm/JS dependencies in the browser playground, prefers runtime ESM loaded from a CDN resolved via automatically generated import maps (the LiveCodes approach) over build-time bundling from node_modules. Confidence: 0.6
- Evaluates technology choices against ecosystem conventions — wants to know whether a capability is common/idiomatic practice in the language's community (and what the standard toolchain does) before investing in it. Confidence: 0.45
- When considering whether to add or keep another engine/language alongside ones already supported, wants it framed as a head-to-head capability comparison — what the new option uniquely adds, overlapping strengths, and each side's advantages/disadvantages — not a standalone feature list. Confidence: 0.55
- Prefers a language be offered as at most two variants: a lightweight one plus one full (typically wasm-backed) compiler, differentiated in a way users notice. Dislikes adding extra engines that are incomplete or approximate versions of the same language — "three partial answers" is worse than one partial plus one real. Confidence: 0.7
- Values a "full" engine variant being genuinely complete in language semantics (real core/stdlib behavior, real analyzer errors, working macros) and would prioritise closing those gaps over ecosystem/breadth features. Confidence: 0.6
- Wants the agent to carry work through to implementation and verification rather than pausing at a plan or diagnosis — after a proven approach, the expectation is to make the code change and report results, not to hand back next steps. Confidence: 0.75
- Expects the agent to keep iterating autonomously until the feature actually works, not to stop and report partial status or hand back a diagnosis/"next experiment" — explicitly says to continue and not stop until it's working. Confidence: 0.7
- Won't accept a known bug documented as a "known limitation"; when a limitation is fixable, wants the real/principled fix, not a workaround or a note in the docs. Confidence: 0.5
